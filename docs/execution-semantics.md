# Execution semantics

Version `3` starts at `entry`. By default it executes one active node at a time; after success, outgoing edges are evaluated in definition order and the first matching target is activated. `$end` completes that path, and the run finishes when no other branch remains. A missing matching edge or invalid expression fails the active node. Cycles require a bounded edge by default; its `maxIterations` limits traversals per run. `allowUnboundedCycles: true` explicitly opts into unlimited loops.
When a node sets `dispatch: "all"`, all matching outgoing edges activate their targets and those nodes run concurrently. A `join.from` list waits for all named predecessor payloads before starting the join node. A run can therefore have multiple active nodes; the persisted active set and partial join inputs let a later `run submit` or `run resume` continue it. See [parallel nodes and joins](graph-and-visualization.md#parallel-nodes-and-joins).

## Executor contract

A workflow file contains exactly one JSON document; trailing tokens, a second document and any other trailing content are rejected by the CLI, workspace, trigger and web loaders before execution. Each node has a non-empty ordered `execution.candidates` list. Every candidate references an executor registered in `executors.json` or a built-in executor and owns its opaque `config` and `session` policy. The registry defines the program entry point, working directory, and environment. Custom names have no graph meaning.

One successful candidate supplies the logical node result. `retry.maxAttempts` is applied to each candidate before fallback is evaluated. The default fallback permits only `start_failed`, meaning the command selected for this invocation was never started. A missing resume or fork command is `configuration_failed`, even when the unused base command is unavailable; only the command the session mode actually launches can produce a startup failure. A launched nonzero process is `exit_code`, a deadline is `timeout`, and result/schema/session failures have their own kinds. An optional `execution.fallback.when` is a boolean Expr over `failure.kind`, `started`, `code`, `timedOut`, `message`, `executor`, and `attempt`, where `attempt` is the 1-based position across the node's whole attempt sequence. A malformed expression fails the node as `fallback_expression` while the completed attempt keeps its executor failure classification. Candidate failures do not traverse business edges.

The invocation directory is the standalone workflow workspace root. Definitions, `executors.json`, optional `triggers.json`, and generated `runs/` live directly in that workspace. Executor directories may be elsewhere, including symlinks to existing agents or paths to external repositories. `AGENTFLOW_ROOT` identifies the workflow root; `AGENTFLOW_WORKSPACE` identifies the executor's working directory. Session policy is independent of directory selection. Resuming persisted session history does not attach to an already running interactive process.

The entry node receives the run input; each selected edge passes the source node output to its target. An edge may declare `map` to construct the target input from `{{ input.field }}`, `{{ output.field }}`, run inputs, and prior node results. An explicit empty `map` sends `{}`. A missing reference in an edge map yields an empty string. An empty run input is an empty JSON object, including after save/reload. Programs read a JSON object from `AGENTFLOW_INPUT_FILE`, write a JSON object to `AGENTFLOW_RESULT_FILE`, and exit with zero status. The runner validates `inputSchema` and `outputSchema` using JSON Schema draft 2020-12. stdout/stderr are logs. The runner alone advances the graph.

The built-in Codex/Claude Code adapters interpret candidate `config.instruction` and optional `config.workspace`. The generic process adapter interprets candidate `config.command`. The engine resolves the selected candidate's session independently of node input. Fixed sessions are scoped to node and candidate executor. Inherit/fork requires a compatible upstream provider; native aliases may share only the same provider, while custom commands require the same registered executor identity. These conventions live in adapters; the graph does not require prompt, decision, or any other business field.

An interaction program can send a message and wait for its callback before writing output. Its node remains active during the interaction; other branches may progress independently in a parallel graph. For recoverable human waits, use an external executor and a separate adapter service; see [the Feishu example](../examples/lark-review/README.md).

The built-in `external` executor instead persists `waiting_input` and releases the run lock. It has no provider session lifecycle, so `session.mode` must be `new`; any other mode fails as `configuration_failed` after session resolution instead of waiting with an empty session. Waiting time starts when that external candidate is selected; work performed by earlier failed candidates remains active time. An independent application can supply output with:

```bash
agentflow run submit <run-id> <node-id> --token <leaseToken> --output '{"score":8}'
```

Adapters pass the waiting node’s `leaseToken` using `--token`. The CLI rejects stale tokens, and the engine checks the token again when applying a queued submission. Every candidate attempt rotates and durably persists the lease token in the checkpoint that installs the attempt, before it is exposed or launched; a delayed callback retained by a failed candidate therefore cannot submit as the retry or fallback that replaced it. Interactive submissions without `--token` are bound to the invocation observed by the CLI before queueing. A queued control is read without being removed; the engine persists the completed attempt and node result, then emits `node.submitted` with the completed attempt's global sequence and candidate coordinates, and only then acknowledges the queue file. A failed state write leaves the request queued with no completion event, so a later executor pass can deliver it instead of losing an accepted result. Accepted output succeeds the node, then edge evaluation continues automatically. The fields and values are defined by the workflow's schema, without built-in business outcomes.

## Persistence and recovery

Every completed visit is appended to `history`. The latest state remains under `nodes.<id>` for expressions and display. Each candidate attempt has a unique visit/candidate/attempt input, config, result, session, stdout and stderr path; failed attempts remain visible in state, events, metrics and Web. Attempt selection, workspace, session protocol, artifact paths and a freshly rotated lease token are saved before launch so a running attempt is observable and an interrupted attempt can be archived without reusing evidence paths. Every completed attempt is persisted together with an explicit continuation decision — retry with the next attempt number, fallback to the next candidate, or terminal — before its completion event is emitted; when fallback evaluation itself fails, the attempt keeps its executor failure and the node records the separate `fallback_expression` terminal cause. Recovery mutations — a resumed continuation, a recovered finished attempt, or an archived orphan — are likewise checkpointed before their events are emitted, so a failed state save cannot leave events claiming an attempt was archived while durable state still records it running. Recovery resumes the recorded continuation instead of replaying a completed attempt. Only an attempt still recorded as `running` is treated as interrupted: that is the inherent uncertainty boundary between process launch and the completion checkpoint, where a process exit may cause the attempt to execute again. AgentFlow does not claim arbitrary external side effects are exactly-once, so programs should support idempotency. Executor registrations are environment configuration, resolved when executing; every candidate name is checked before a run is created or resumed. Availability failures remain candidate evidence, but a missing registration is a workflow setup error and cannot select fallback. A later retry or resume uses current registrations, while session compatibility is checked against the provider protocol recorded when the session was created.

`run retry` archives each failed node as a visit before allocating a fresh visit and attempt sequence, preserving successful siblings in parallel runs. `run resume` records a node whose last attempt is still `running` as an interrupted attempt, archives that visit, and reopens execution at that attempt's recorded candidate and retry position in a fresh artifact namespace; that interrupted candidate may therefore execute again, while earlier candidates and retry attempts whose completion checkpoints were already acknowledged are not selected again. When the last attempt already completed, resume follows its persisted retry/fallback/terminal continuation without replaying it. AgentFlow does not claim arbitrary external side effects are exactly-once, so programs should support idempotency. Controls are queued when the run is locked, and every applied cancel, retry or submission is checkpointed before its completion event and acknowledged after that checkpoint. Cancellation is processed at executor boundaries; stopping a currently running child immediately is not implemented.
