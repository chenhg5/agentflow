# 设计与验收指引

目标是让另一个 agent 或人能理解、运行并修复整个流程。设计可以写在
DESIGN.md 或已有 RUNBOOK 中，不增加图的业务字段，也不要求固定角色数量。

## 1. 职责与输入输出

先从任务的实际交付倒推职责。需要判断、研究、创作的工作交给有适当上下文
的 agent；确定性变换、API 调用、构建和数据采集可由普通程序完成。已有程序
有价值就复用，迁移不等于把每段脚本包成节点，也不要求把确定性工作改成模型。

为每个节点说明收到什么、产生什么、什么证据说明职责完成。JSON Schema 要
体现下游真正需要的字段与类型。多分支结果使用可区分的形状或字段；不凭一个
进程退出码推断业务任务成功。大型产物可传路径、版本/内容标识及摘要，下游
使用明确输入定位，避免按“今天”“最新”重新猜共享文件。

验证字段保真：任务 ID、仓库 ref/head、证据身份、审核意见等关键数据在经过
程序、分支、汇合、人工等待与返工后仍能追溯。策略属于 config，任务数据随边
传递，稳定上下文属于角色资源；不要将它们全部复制进全局 inputs。

## 2. 角色与上下文

逐个认知职责给出下面的信息；可以用一张表，不必创建独立的抽象角色系统：

| 项 | 需要回答的问题 |
| --- | --- |
| 职责 | 完成什么判断/交付，哪些工作交给其他节点或人？ |
| 指令 | 哪份原生常驻指令或明确的外部角色来源会被使用？ |
| 上下文 | 要读哪些政策、代码/知识、版本和输入证据？哪些信息不应进入此角色？ |
| Skills | 哪些重复步骤值得封装或复用？不需要额外 skill 时说明理由。 |
| 工具 | 需要哪些工具、如何加载、输入输出是什么、允许哪些外部副作用？ |
| 目录 | 是新建的专用目录、软链，还是已核验的外部 agent？与目标仓库路径分开解释。 |
| Session | new/fixed/inherit/fork 的理由是什么？多个 provider 候选如何隔离会话？ |
| 验收 | 用什么非空任务证明角色读取了必要上下文、调用了必要工具并完成工作？ |

专业身份来自指令、上下文与能力组合；单个模型名、CLI 名称或通用项目目录
不构成专业角色。新建角色时改写 initializer 的通用说明，使其体现实际职责。
外部 agent 可以完全保留原目录，不为满足目录外观而复制/改写它的资源。

Codex 使用自己的 AGENTS.md / skills / 本地工具配置，Claude 使用对应原生文件。
共享领域材料可以通过显式引用复用；不要将一个 provider 的配置直接复制给另
一个。workspace validate 的资源摘要是发现结果，实际加载仍要用运行证据确认。
不要通过修改全局 provider 配置让案例通过。

## 3. 边与运行策略

画清楚每个结果的去向，包括未命中、失败、降级与人工转交。明确每条边的
输入映射，first 与 all 的选择，以及 join 等待哪些直接前驱。需要返工时明确
返回哪个节点、传哪些意见、如何保持任务身份，以及次数上限到达后会发生什么。

不要让 executor 自己改 run state 或偷偷执行下一个角色。候选 fallback 是本节点
执行策略，业务分支属于 edges。将“审查不可用”作为降级结果可以是合理业务
选择，但它的后继与验收应明确区别于“完成审查”。

## 4. Human in the loop

先确定人要作出的判断与需要看到的证据，再选择终端、网页、IM 或其他程序。
说明允许返回的 JSON 及每种输出所走的边；名称任意，图不识别 approve/reject
等业务词。需要修改时把意见和原任务一起传回指定角色。

长等待优先 external + 独立适配器。适配器负责通知、身份、事件关联、交互记录
与回传；引擎负责输出 schema、waiting 调用 token 和边推进。验证旧卡片、重复
点击、无效输出不会推进错误的一次访问。区分“人的选择已保存”“引擎已接收”
和“后继已完成”，使失败与重启时的状态可解释。

明确是否需要截止时间、提醒、取消或升级处理，并在工作流/适配器中实现和
测试对应策略；没有实现时记录能力缺口，不能只写一句超时政策就算支持。
用真实人工动作验证端到端渠道；自动 submit 可以测试图的契约，但不能声称
已经验证 IM 回调或人类审核。发送消息和产生外部业务副作用遵循任务授权。

## 5. 完成与迁移

交付同时包括设计、图、角色/程序资源、RUNBOOK 与证据。逐节点标记：已做
静态检查、替身契约运行、真实模型执行、真实人工回传，或尚未覆盖。模型输出
一个预设空 JSON 只能证明结果通道；至少使用一份真实结构的非空任务核对角色
完成了关键判断，保留上下文版本、调用与产物证据。

迁移旧项目时，除了边语义，还要核对旧流程中的认知职责、实际上下文、工具、
身份、共享数据依赖与人类决策如何承接。原程序通过格式迁移后仍可能缺少这些
设计。用原项目的代表案例加失败/返工案例验收，而不是把工作量设成零来得到
绿色整图结果。结构检查、执行可靠性和业务质量分别报告。
