# 写好一条 workflow 的原则

这份讲**怎么设计**：先对齐什么、怎么省时间和钱、权限和密钥怎么放、怎么跟人沟通、开发时怎么验。图怎么写、命令怎么敲见 [SKILL.md](../SKILL.md)，节点契约和验收见 [design.md](design.md)。三份都读完再动手。

这些原则不绑定任何通信渠道或平台：IM、邮件、网页、终端都由 executor / 适配器实现，图只认 JSON 和边。

## 1. 先跟人对齐，再写图

开工前用业务语言跟需求方确认下面几件事，回放成一段大白话加一张流程图（`agentflow web workflow.json` 或 Mermaid），请他确认「是这个流程吗」。确认后写进 `DESIGN.md` 顶部：

| 要说清的 | 例子 |
|---|---|
| 什么时候跑 | 每个工作日 9:30（写明时区）/ 有 PR 合进 main / 收到一条 webhook |
| 读什么、写什么 | 读某仓库的 PR；往一个群发一条消息；不改任何代码 |
| 谁拍板、拍什么 | 负责人选一版文案；一天没人回就不做 |
| 出错了怎么办 | 告诉负责人「这次没做出来，原因……」，不自动重试第二遍 |
| 一次花多少 | 只调一次便宜模型，最多 $1 |

- 只问业务问题，不问「用哪个 executor」「schema 怎么写」这种你该自己决定的事。
- 用户说不清的地方给两三个选项让他挑，不要猜一个就开写。

## 2. 权限只要用得到的

- 每个 executor 只拿到它真用的东西：`environment` 用 `allowlist` 列出要继承的变量，密钥经受控 wrapper 注入；仓库、表、群写到具体的那一个，能只读就只读。
- **权限范围先跟人确认**：这条 workflow 会读哪些、写哪些、结果谁看得到，写进 DESIGN.md，负责人同意后再配。
- **对外写操作先只记不做**：发消息、开 PR、改数据、调第三方写接口的节点，先支持一个运行输入（如 `mode=shadow`），shadow 下只把「本来会做什么」写进结果和 `summary`。跑过几轮、负责人看过记录再切成真写。
- 真写之前有人拍板的，用 `external` 节点等人，`outputSchema` 写清允许的选项；过期就走「不做」的边，不默认批准。

## 3. 什么时候开始：有事件就用回调

- 外部系统有事件（PR 开了、issue 建了、报了新错），用 `triggers.json` 的 webhook，秒级起、不空跑；只有「每天 / 每周」这种按时间的才用 cron。
- **同一件事会来好几次**：PR 每推一次都是一次事件。用 delivery ID、`--idempotency-key`（例如 `pr-<号>-<head sha>`）或业务自己的去重记录，只订真正要的事件类型。
- 测试和正式各一份工作区时，别让两边都接同一个事件来源，否则一个事件跑两轮、对外写两次。

## 4. 效率：能用程序就别开 agent

先选最轻的做法：

| 要做的事 | 怎么做 | 大概多快、多少钱 |
|---|---|---|
| 调 API、读写数据、拼报告、按固定规则判断 | `process` 或自写程序 executor | 毫秒到秒，不花模型钱 |
| 是非题、选择题、打分、抽字段、写一小段文案 | 程序里直接调一次便宜模型的 API | 秒级，几分钱 |
| 改代码、跑测试、多步摸索、要用工具 | `codex` / `claude-code` 节点 | 分钟级，几毛到几块 |

- agent 节点**只做模型才能做的那一段**：拉代码、装依赖、准备输入、收尾、发通知都拆成程序节点，别让 agent 去做能写死的事。
- 能并行的用 `dispatch: all` + `join`；等人的节点是 `waiting_input`，不占 run 名额。
- 步骤本身由数据决定、写成 JSON 图很别扭时，用 `agentflow code run`，在脚本里 `code step` 记录每一步。

## 5. 模型：够用就好，设上限

- 默认先用便宜的档（fast 档模型），在测试数据上跑几轮看效果，不够再升一档；真的难（大改动、要自己定方案）才用最强的。
- 在候选的 `config` 或 agent 自己的配置里写死型号，别依赖「默认模型」——默认会变。
- 给每次调用设花费或轮数上限（例如 `claude -p --max-budget-usd`、`codex` 的模型与推理档位），并在 DESIGN.md 写一次运行的预算。
- 不同的活用不同的候选：改前端用一个 agent、审代码用另一个、跑数据的节点不带 agent。只是 provider 不可用时的替补写 `execution.fallback`，不要用它切换业务角色。

## 6. 第三方、密钥、网络

- **第三方**：有现成 executor / 适配器就复用；没有就写一个程序 executor 把它封起来，令牌只在这个程序的受控环境里。不要把令牌硬写进图、`config`、run input 或 agent 的指令里。
- 业务数据库给**只读角色**，查询放程序节点里做，不让 agent 拿连接串。
- **密钥分测试和正式两套**：测试用测试账号、测试数据，别拿正式的 key 去测。值从文件或 stdin 进 wrapper，不进仓库、聊天和日志。配之前跟人确认这把 key 能动哪些数据。
- **网络**：executor 要访问的业务域名写进 DESIGN.md 并过 review；agent 的沙箱或网络限制由 provider 自己的配置管，不要为了让 demo 通过去改全局配置。

## 7. 要不要留会话、留记忆

| | 是什么 | 好处 | 代价 | 什么时候用 |
|---|---|---|---|---|
| `session.mode: fixed` | 同一个 run 里重访节点接着同一个会话 | 返工时 agent 记得上一轮的意见和改动 | 上下文越来越长、越来越贵 | 一轮里要等人反馈再接着改 |
| `session.mode: new` | 每次空白开始 | 便宜、可复现 | 不记得之前 | 每次都独立的活（默认） |
| 业务记录（文件 / 数据库） | workflow 自己的长期数据：上一轮的基线、去重表、错题本 | 跨 run 记住结论 | 要自己维护格式和清理 | 跨运行要记住的东西；不要指望引擎或会话替你记 |

- 给 agent 留笔记时让它记结论，不记过程（「标题 12 字以内」，而不是「第三轮我试了……」），并定期清掉过时的。

## 8. 跟人沟通（最重要）

最常卡住的是跟人对齐。凡是要人看、要人拍板的消息（不管经哪个渠道发），守住这几条：

1. **说大白话**：写给不看代码的人。不说「本次变更涉及 3 个模块的重构」，说「登录过期以后，现在会提示重新登录，不会白屏了」。
2. **结论先行**：最上面一两句结论 + 要人做的决定；理由、过程、文件列表、链接放到后面或收起来。
3. **摆例子：改前怎样、改后怎样**，能配截图或短视频更好；图表只给本身就在看数的事（趋势、占比），别为一两个数画图。
4. **一条消息只问一件事**：选项写动作（「发」「先不发」「改短一点」），别写「确认 / 取消」；只 @ 真正要拍板的人；时间写明时区。
5. **人说了话先回个「收到」**，再慢慢做；做完在同一个消息串里回结果，别另起一条。
6. **失败也说人话**：「这次没做出来：连不上 xx（网络没放开），已经记下，修好会重跑」，别贴一屏报错。
7. **要人细看的给链接**：Hub 的运行页（`<hub>/runs/<machine>/<run-id>`）把每一步、流程图、耗时、日志尾和产物都画出来了，消息里放结论、细节给链接。
8. **让每一步自己说清楚**：节点结果里写 `summary`（这一步做了什么）和 `reason`（为什么这么判断 / 为什么跳过），Hub 和 `agentflow hub run` 都会显示。

适配器负责把这些落到具体渠道（卡片、邮件、网页表单），图里只放 `external` 节点、输出契约和边。

## 9. 开发时：先把环境和第三方拆开验，别每次跑全程

workflow 能不能跑通，很大程度取决于环境：密钥配没配、权限够不够、网络通不通、环境变量带没带、第三方配额、令牌会不会中途过期。跑一次全程动辄几十分钟、还要花钱，最亏的是跑到第 40 分钟才发现一个小配置不对。按这个顺序来：

**① 分三层，各层单独能验**

| 层 | 是什么 | 怎么验 | 多快 |
|---|---|---|---|
| 纯逻辑 | 解析、判断、算分、拼消息文案 | 写成普通函数，配几份固定测试数据（`fixtures/`），本地单测 | 秒级 |
| 外部依赖 | 每个第三方、每把密钥、每个连接、agent 的登录和工具 | 每个单独调一次最便宜的只读接口（见 ②） | 几十秒 |
| 编排 | 图把上面串起来、等人、发通知 | 前两层都过了，最后才跑全程 | 分钟到几十分钟 |

**② 开工第一件事：把依赖单独探一遍**

- `agentflow workspace validate --format json`、`workflow validate --check-executors`：图、注册表、入口程序对不对得上。
- 留一个**探针模式**：运行输入 `probe=true` 时，第一个节点对每个外部依赖调一次只读接口（健康检查、whoami、列一条记录），把通不通写进结果和 `summary`，然后走到 `$end`。
- agent 节点先单独起一次、只让它回一句固定 JSON，确认登录、工作目录和工具加载了，再给它真任务。

**③ 用运行输入只跑需要的那一段**

在 `inputs` 里约定几个开关，用边条件让试跑只做要验证的部分：

```json
{
  "inputs": {
    "probe": {"type": "string"},
    "fixture": {"type": "string"},
    "stop_after": {"type": "string"},
    "reuse": {"type": "string"}
  },
  "edges": [
    {"from": "preflight", "to": "$end", "when": "inputs.probe == 'true'"},
    {"from": "preflight", "to": "fetch"},
    {"from": "fetch", "to": "$end", "when": "inputs.stop_after == 'fetch'"},
    {"from": "fetch", "to": "make"}
  ]
}
```

```bash
agentflow run start workflow.json --input probe=true --format json
agentflow run start workflow.json --input fixture=pr-1045 --input stop_after=fetch --format json
```

- `--input` 传进来的值都是字符串，条件里写 `inputs.probe == 'true'`；没传的开关不会让条件报错，直接走后面的默认边。
- `fixture` 让取数节点读固定测试数据代替真实来源；`reuse` 让贵的节点读上次存档的结果。
- 这些开关**只能让这一轮少做、换数据**，不能用来跳过审批、放大权限或改写对外写操作的目标。定时和 webhook 触发不带它们，照常跑全程。
- 还没有真实 agent 时，用临时注册表把 agent 换成替身程序验证数据契约（见 SKILL.md「验证与运行」），并写明模型行为没验证。

**④ 贵的放后面，做完先存档**

agent 这类又慢又贵的节点，做完先把结果存下来（推分支、写产物并在结果里返回路径），后面的节点挂了用 `run retry` / `run resume` 只补后面的，不重跑贵的。

**⑤ 第一步就检查前置条件，失败得快**

第一个节点（`preflight`）检查这一轮要的东西齐不齐：密钥、连接、环境变量、配额、输入数据。缺了马上用一句大白话报出来，别等到第 40 分钟才在某个命令里爆。

**⑥ 每次跑全程之前问自己一句**：这一轮要验证的是什么？如果只是验一个配置、一个第三方，能不能用探针或开关在一分钟内验完？

## 10. 上线以后：用数据找该修的地方

workflow 跑起来以后，别凭感觉改。接了 Hub 的话（`docs/hub.md`），用 CLI 拿数据：

```bash
agentflow hub steps --workflow <名字> --days 7     # 哪一步最常失败、重试、等人最久，最常见的错误是什么
agentflow hub runs --workflow <名字> --status failed --format ndjson
agentflow hub run <machine>/<run-id>               # 失败那一轮：每一步的错误、日志尾、结果、产物
```

先修 `hub steps` 排在最前面的那一步：失败多的看 `errors` 里的消息和 `last_run_id`，慢的看 p95，等人久的看是不是消息没说清楚、该提醒没提醒。改完对比改前改后的成功率和耗时（`hub workflows`、`run compare`）。

## 11. 出错了：先分诊

| 类别 | 谁处理 | 怎么做 |
|---|---|---|
| AgentFlow 本身的问题（CLI 崩溃、状态不一致） | AgentFlow 维护人 | 重试一次；还不行带上 `run get` / `run logs` 的输出提 issue |
| 权限或接入（401/403、缺密钥、网络不通） | 有权限的人 | 说清缺什么、为什么要，请他配，别让需求方自己摸索 |
| 业务没定义清楚（不知道该走哪条边） | workflow 负责人 | 用业务语言问一个问题，给选项 |
| 代码 bug（程序或 agent 指令写错） | 你自己 | 自己修，补一份能复现的测试数据 |

## 12. 交付之前

- [ ] 需求按第 1 节问过，DESIGN.md 顶部写了大白话的需求表，用户确认了流程图
- [ ] 权限范围、密钥、要访问的域名都跟负责人确认过，写在 DESIGN.md
- [ ] 对外写操作有 shadow 模式或人工拍板；过期走「不做」
- [ ] 能程序化的没用 agent；用了 agent 的写死了型号、设了花费上限
- [ ] 会话策略想清楚了：要接着改的才 `fixed`
- [ ] 给人的消息：结论一两句大白话、有例子、细节收起来、给了 Hub 运行页链接；节点结果有 `summary` / `reason`
- [ ] 纯逻辑有单测和固定测试数据；外部依赖单独探过；第一步检查前置条件
- [ ] 用代表输入跑通至少一轮，失败、返工、拒绝的路径也试过（见 design.md 第 5 节）
