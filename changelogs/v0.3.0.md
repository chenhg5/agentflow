# v0.3.0 — Ordered executor candidates

Preview release. A logical node can select from several ordered executors, including native agents, custom programs and external input adapters.

## Execution and observation

- Add ordered `execution.candidates`, each with independent executor config and session policy. Retries are per candidate; a successful candidate supplies the node's output and advances its outgoing edges.
- Default fallback handles OS process startup failures. Configure `execution.fallback.when` with Expr and structured failure fields for other cases. A program that starts and exits unsuccessfully does not trigger default fallback.
- Isolate candidate sessions, attempt artifacts and submission tokens. Persist completed attempts and retry/fallback continuations before completion events; resume preserves the candidate and retry position.
- Preserve queued external submissions until their state is saved. Improve parallel waiting-time accounting and freeze finished/cancelled metrics.
- Show selected executors, attempts, captured logs, input and output in CLI state and the Web inspector. Improve remembered browser language selection.
- Tighten raw workflow JSON validation, command/session preflight and fallback-aware workspace resource diagnostics.

## Authoring and adapters

- Add role-first authoring guidance, a `DESIGN.md` scaffold, owned Claude Code agent scaffolding, and candidate-local instruction/skill/tool resource discovery.
- Add an existing-project migration benchmark with human rework, stale/invalid submissions and changed-input cases.
- Honor Claude Code model and stdin prompt options and delimit task arguments correctly.
- Include a recoverable Feishu card adapter example with configuration, setup guidance and tests. It remains a separate program; the graph has no Feishu-specific semantics.

## Breaking workflow schema change

Workflow version remains `3`, but the old node-level `executor`, `config`, and `execution.session` fields are rejected. There is no compatibility decoder. Move them into a candidate, even when there is only one executor:

```json
{
  "id": "work",
  "execution": {
    "candidates": [
      {"executor": "primary", "config": {}, "session": {"mode": "new"}},
      {"executor": "backup", "config": {}, "session": {"mode": "new"}}
    ]
  }
}
```

Update existing workflow files before upgrading. Built-in `external` candidates support only the default/new session policy.

## Known limitations

Independent review has not accepted the entire change set. Two static validation issues remain: an inherited session with several possible source protocols, or a conditional revisit of a fixed session, can reach an external waiting fallback that the validator does not recognize. In a parallel graph, this can incorrectly classify another node's result as already available and misreport candidate/session availability. Static validation is not a guarantee that these paths can run; exercise the intended paths before relying on them.

Interrupted programs may replay when completion was not durably recorded; executors with external side effects need idempotency. Captured logs are available, but general live provider tool-event streaming and uniform token/cost reporting are not included.

## Verification

Local release checks passed: `make check`, `make test-e2e`, `make test-benchmark`, targeted engine/store/driver race tests, Web UI checks, and the Feishu adapter's simulated-transport tests. The separate candidate CLI suites passed 233 cases (21 execution, 29 lifecycle, 183 validation). These passing checks do not resolve the independent review findings listed above.
